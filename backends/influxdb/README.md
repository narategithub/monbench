# influxdb backend

Writes the benchmark data set to, and queries it from, a single **InfluxDB 3**
server. Unlike `sos`/`dsos`, it is not partitioned across the server nodes: each
server node generates its own partition and sends it to the same InfluxDB
server, so together the nodes write the whole data set once.

## What it supports

| | |
|---|---|
| Write | Yes, to one InfluxDB 3 server (`INFLUX_HOST`) |
| Query | Yes, via the Python client (Arrow Flight) or the HTTP query API |
| Reads data written by | `influxdb` |
| Service | Yes (`PLUGIN_SERVICE=1`); the harness starts and stops `influxdb3` and generates its admin token |
| Partitioning | Data is generated per server but all sent to one server, not sharded |
| Component kinds (design/value-generation.md Sec 6) | Yes -- see "Component-kind data model mapping" below |

## Data model mapping

The data set maps to InfluxDB as:

| Data set | InfluxDB |
|---|---|
| data set name (`{schema}`) | measurement (table) |
| `component_id`, `job_id` | tags |
| every other attribute (`seq`, `MemTotal`, `free`, ..., `procs_blocked`) | fields (`seq` kept so rows can be identified in verification) |
| `timestamp` | point time |

## Component-kind data model mapping

A dataset may also declare component kinds (design/value-generation.md Sec
6) -- a flat (scalar-attribute) record type with a variable, per-sample
instance count, nested one level below the node (e.g. `cpu`, `netdev` in
`dataset/curated_metrics_like.json`). Each kind gets its own InfluxDB
measurement, generic over however many kinds a dataset declares:

| Component kind | InfluxDB |
|---|---|
| kind name | measurement `{schema}_<kind>` (e.g. `monitoring_nested_cpu`) |
| `component_id`, `job_id`, `component_index` | tags |
| the kind's own attributes, plus `seq` | fields (`seq` kept for the same reason as the flat measurement's) |
| `timestamp` of the node sample this instance belongs to | point time |

A component measurement joins back to the flat node measurement on
`(component_id, time)` -- that pair already uniquely identifies
`(component_id, seq)`, and `job_id` is a deterministic function of `seq`
(`1 + seq // JOB_LEN`), so it never disagrees with that join. A query
translating the `match.where` grammar's `kind[i].attr`/`kind[*].attr`/
`count(kind)` conditions (design doc Sec 6.5) into native SQL joins the
node measurement to the kind's measurement this way, filters on the
kind's fields (and `component_index` for the `kind[i]` form, or a
`GROUP BY component_id, time HAVING COUNT(*) ...` subquery for
`count(kind)`), and selects the *node* measurement's columns -- so the
result is still node-shaped rows that `core/bench.py`'s existing
verifier (which recomputes the expected node-row set, not component
rows) can check unchanged. See `queries/curated_metrics.json` for worked
examples against `dataset/curated_metrics_like.json`.

A dataset with no `"components"` declared (e.g. `dataset/default.json`)
writes and queries exactly as before -- `influx_write.py` writes no
component measurements and `queries/default.json` has no `match.where`
of this form.

## Write methods

One writer, `writer/influx_write.py`, with a selectable interface:

| `INFLUX_INTERFACE` | How it writes | Extra dependency |
|---|---|---|
| `python` (default) | the `influxdb_client_3` library, batched | `pip install influxdb3-python` |
| `http` | POST line protocol to the v3 write API | none (standard library only) |

Select the writer with `WRITERS=influx` (it is the default for this backend).

## Query methods

The query adapter supports InfluxDB 3's two query languages, selected with
`INFLUX_QUERY_LANG`:

| `INFLUX_QUERY_LANG` | Language |
|---|---|
| `sql` (default) | SQL |
| `influxql` | InfluxQL |

The interface for querying follows `INFLUX_INTERFACE` (the `python` client uses
Arrow Flight; `http` uses the query API). Query strings for InfluxDB go in a
query set under the `influxdb` adapter name. Component-kind queries (see
above) need the `sql` dialect -- InfluxQL has no JOIN.

## Configuration

Settings live in `backends/influxdb/influxdb_backend.conf` (override from the
environment):

| Setting | Default | Purpose |
|---|---|---|
| `INFLUX_HOST` | `http://<first SERVER_NODES host>:8181` | InfluxDB 3 server URL, reachable from all nodes |
| `INFLUX_DATABASE` | `monbench` | Database to write to and query; created automatically by `plugin_serve_start` |
| `INFLUX_TOKEN_FILE` | `${RUN_DIR}/influxdb3-token.json` | Path to the admin token file generated by `plugin_serve_start`; set automatically, override only if managing the token yourself |
| `INFLUX_INTERFACE` | `python` | `python` or `http` (write and query) |
| `INFLUX_QUERY_LANG` | `sql` | `sql` or `influxql` |
| `INFLUX_PRECISION` | `s` | Line-protocol timestamp precision: `ns`/`us`/`ms`/`s` |
| `INFLUX_WRITE_BATCH` | `10000` | Records per write request/batch |
| `INFLUX_DATA_DIR` | `${RUN_DIR}/data/${HOSTNAME}` | `influxdb3`'s data directory on each server node; override to place data on a specific mount |

### Examples

```bash
# Write with the Python client (default)
WRITE_BACKEND=influxdb bin/run.sh -l ssh write

# Write with the HTTP interface (no client library needed)
WRITE_BACKEND=influxdb INFLUX_INTERFACE=http bin/run.sh -l ssh write

# Choose the query language
QUERY_BACKEND=influxdb INFLUX_QUERY_LANG=influxql bin/run.sh -l ssh check
```

## Requirements

- An InfluxDB 3 server reachable at `INFLUX_HOST`. Auth is handled by the
  harness: `plugin_serve_start` generates an admin token offline and creates
  `INFLUX_DATABASE` before the write or query steps run — no token or
  database needs to be set up in advance.
- For the `python` interface: `pip install influxdb3-python` on the write (and
  query) nodes. The `http` interface needs only the Python standard library.
